# 课程插件（三个包）

学生端与教师端是**两个可独立安装的插件**，加一个共享内核。三者可以装在同一个
DSH 进程里同时运行 —— 这正是老师要在一台机器上对测两端的前提。

```
course-plugin/
├─ dsh-course-core/      共享内核（不是面板，没有侧栏入口）
├─ dsh-course-student/   学生端面板
└─ dsh-course-teacher/   教师端面板
```

## 为什么必须拆成两个插件

原本是一个插件、靠环境变量 `CIP_ROLE` 裁剪界面。那样有个绕不过去的问题：
**两边要同时看到自己的面板**，就得同时挂两个面板入口 —— 一个插件只能注册一个。

拆开之后，硬约束只有一条，来自 DSH 本身：

> `webServer.register` 对重复的 `(kind, path)` **直接抛错**。
> 路由模式属于「组合级契约」，撞车就是配置错误。

所以两个插件各带自己的路由前缀：

| 包 | 路由前缀 | 侧栏面板 id | 调用模型 |
| --- | --- | --- | --- |
| `dsh-course-student` | `/cip-stu`（`-media` `-katex` `.css` `-api`） | `course-student` | **是**（费用归学生） |
| `dsh-course-teacher` | `/cip-tea`（同上） | `course-teacher` | 否 |

`/cip-stu` 与 `/cip-tea` 不重叠，所以两个插件能共存；换成同一前缀，第二个注册直接抛错。

## 为什么要有共享内核

两边重叠的部分很多：工作区解析、课程索引、课件与教案读取、问题条目读写、
markdown/公式渲染、模型调用。复制两份的话，改一处忘一处就会开始漂移。

这个项目已经因为「两边对同一个字段的理解不一致」吃过一次大亏：
宿主以为自己在给 `media[].file` 拼完整 URL，客户端也以为自己拿到的是完整 URL，
于是 `/cip-media/第一章//cip-media/第一章/x.png` → 400 → **所有图片都加载不出来**。
所以共享的部分一律只有一份。

### 客户端也共享

`dsh-course-core/lib/client-shared.js` 是**构建产物**，由
`课程发布/tools/extract-client-core.cjs` 从已经验证过的客户端里抽段生成
（markdown→HTML、KaTeX 加载、课程脉络树、图片组件）。
两个插件通过 ModuleLoader 的 `require('dsh-course-client-core')` 拿它。

重建 + 校验一条命令：

```sh
node 课程发布/tools/build-clients.mjs
```

它会：抽段 → 物化三个 bundle → 校验双插件挂载与端到端流程。

## 公共数据面

两个插件通过**同一个课程工作区目录**交换数据。目录分工保证每个位置只有一个写入方：

| 目录 | 谁写 | 谁读 |
| --- | --- | --- |
| `课程问题池/公共/` | 教师端（审计为「值得共享」时写副本） | 学生端、教师端 |
| `课程问题池/学生/<学号>/` | 该学生自己 | 教师端（全量）、本人 |
| `作业提交/<学号>/` | 该学生自己 | 教师端（全量）、本人 |
| `课程中心/` | 公开仓分发 | 两端 |

**「值得共享」是写副本，不是移动**：原条仍留在该学生的私有目录里，
他的历史不会因为老师的一次操作而消失。

同步靠 git：老师 `course-repo.mjs publish` + push，学生 pull。
插件里能看到待发布清单，但不替你做 git（凭据不该进插件）。

## 三项功能对应的实现

### 1. 两个独立插件 + 文件上传下载入口 + 教师归档

- 两个包各自可装，面板独立（见上表）
- **上传**：学生端「作业批改」选课时 + 传文件（`.py/.ipynb/.md/...`，上限 4 MB）；
  教师端「学生提交」能读任意学生的全文
- **下载**：公开面随公开仓分发，`公开问答.json` 是它的结构化清单 ——
  学生端「公开问答」页直接读它，不必逐个解析 markdown
- **归档**：教师端可改标题/总结/写归档说明；「归档发布」页里能**直接跑发布工具**
  （check / publish 两个按钮，真的 spawn `course-repo.mjs`），
  只把 git commit/push 留给老师手动 —— 那一步用他的凭据，插件里不放任何人的密钥

### 2. 每一轮追问都有 AI 作答 + 问答公开 + 统一风格的凝练标题

- **每一轮都真的调模型**，`followup` 不看轮次，追加一轮答一轮
  （`MAX_THREAD_TURNS` 默认 40，只为防误触烧额度）
- 线程结构化存在同目录的 `<条目名>.thread.json`，md 里另有一份给人读的渲染
  —— 多轮问答里有代码块和 `$公式$`，塞回 md 再解析极易出错
- **标题凝练**用 `TITLE_SYSTEM`：12–24 汉字、直陈困惑点、禁「关于…的问题」这类外壳。
  整个问题池因此看起来像一个人写的。老师可在审计时覆盖 —— 公共池的措辞由老师负责
- **问题总结**用 `SUMMARY_SYSTEM`，同一套口径，轮次增加后会重做
- **他人可见**：老师标为「值得共享」后写一份副本进公共面，
  学生端「公开问答」页看到完整问答与总结
- **教师答复**（`answer` 动作）：老师可以不先决定去向就直接答复学生，
  答复以 `by:'teacher'` 进线程；学生端把它**单独提到最前面**显示 ——
  教师答复与 AI 草稿的可信度不是一个级别，埋在几十轮里等于没有。
  若该条已公开，公共面那份同步更新，否则两边内容会不一致
- **费用**：每次模型调用记 tokens 进条目，学生端「额度」页累加显示

### 3. 按教案批改 + 记录问题 + 教师端沉淀共性

- 批改以**教案为对齐基准**（`GRADER_SYSTEM` 第一条就是这条）：
  教案要求手写实现、学生调库绕过，必须指出来，不因结果对就算过
- 模型须以 `### 问题清单` 收尾，每行 `- [严重度] 描述（证据）`；
  宿主 `parseIssueList` 解析后逐条落成学生私有条目
- 教师端「共性问题」的判据是**几个不同学生**踩到，不是一个人问了几次：
  一个人反复问是个人困惑，三个人各问一次才是教案或讲法的问题
- 每一组可整批标为共享/私有，界面给出沉淀去向建议

## 已知边界

- **`/cip-stu-api`、`/cip-tea-api` 无鉴权**。假定只绑在本机回环或受信隧道后面。
  两个插件的角色差异是**界面与工作流**的差异，不是网络安全边界 ——
  学生端插件装在学生机器上，那里的工作区只有他自己那份数据，看不到别人的。
- 工作区解析三级：`CIP_WORKSPACE` → `~/.dsh/cip-workspace.txt` → 内置默认值，
  每级都验证目录里确实有 `课程中心/`。
- 学生身份取 `CIP_STUDENT`，缺省回落到系统用户名。

## 安装

```sh
dsh plugin --profile web add <本目录>/dsh-course-student
dsh plugin --profile web add <本目录>/dsh-course-teacher
dsh plugin --profile web add <本目录>/dsh-course-core
```

三个都要装：两个面板各自 `require` 核心的宿主半区与客户端半区。
`课程发布/tools/switch-profile.mjs` 会一次改好 profile 的 dependencies 与
`dsh.profile.bundles`（两处必须同时改对，否则装了不挂载且无提示）。
